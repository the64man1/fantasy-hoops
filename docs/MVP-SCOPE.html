Fantasy Basketball: MVP Scope & 8-Week Plan

A single-league head-to-head 9-category fantasy basketball app, live for opening night. Drafting stays on Yahoo; everything after it moves here.

Drafted13 Aug 2026 Window17 Aug – 11 Oct Target2026–27 opening night Team1, part-time

The bet

One league of real people plays a full season on this app without touching Yahoo after roster import. That is the whole success condition. Everything in this document either serves it or is deferred.

The scope is set by a fixed external deadline rather than a feature list. Tip-off doesn't move, so the plan is built to be cut, not extended — see the ordered cut list at the end.

Reality check

Eight weeks part-time is roughly 120–160 hours. That is tight for what follows. The plan assumes you will invoke the cut list at least once; treat that as expected, not as failure.

Assumptions

  • The draft happens on Yahoo. The commissioner transcribes final rosters once, by hand or CSV.
  • Yahoo's Fantasy Sports API is the source of truth for players, position eligibility, injury status, and box scores.
  • One league. The schema is multi-tenant; there is no league-creation UI.
  • Head-to-head 9-category only. Weekly matchups, Monday–Sunday.
  • Responsive web. No native app.
Confirm before week 1

The 2026–27 NBA season start date. This plan assumes late October, which puts preseason in week 7 and leaves roughly ten days of slack after week 8. If tip-off is earlier than expected, the cut list moves up rather than the schedule compressing.

Scope

Live on day one

10 items · the daily loop

Set a lineup, see if you're winning, fix your roster when someone gets hurt. Nothing else is load-bearing.

  • Player universe sync — names, NBA team, position eligibility, injury status
  • Stat ingestion — nightly box scores, idempotent
  • Daily lineup setting with slot-eligibility validation
  • Per-player lineup locking at tip-off
  • Scoring: H2H 9-cat, category win/loss/tie
  • Season schedule generation and standings
  • Free agency: immediate add/drop
  • Matchup view — your categories vs. your opponent's
  • IL slots
  • Commissioner admin: edit any roster, force any transaction, correct any score

Deferred

Safe to ship in-season or never

Each of these is either episodic, months away, or replaceable by a commissioner acting manually.

  • Draft room — happens on Yahoo
  • Waivers (FAAB or priority) — replaced by first-come-first-served free agency
  • Trade workflow — commissioner executes via admin; propose/accept/veto is a real state machine and deserves proper design
  • Playoff bracket — not needed until March
  • Roto and points formats
  • Keepers and dynasty rules
  • Transaction limits, games-played caps
  • Notifications, message board, player news
  • Projections and advanced stats
  • Native mobile
Known cost of the waiver cut

First-come-first-served free agency produces 3 a.m. races over streaming pickups, and your league will complain about it. It is still the right cut — waivers are a whole scheduled-claim subsystem with bid resolution and tiebreaks. This is the obvious v2.

Subsystems

Build stance follows the portfolio logic: hand-own the parts you will be interviewed about, delegate the parts that are plumbing. Own means write it yourself and be able to defend every decision cold.

Subsystem Responsibility Stance Primary risk
Provider gateway OAuth token lifecycle, request throttling, translation from Yahoo's shapes into domain models Mixed Yahoo returns XML by default and deeply nested JSON on request; without an anti-corruption layer their shapes leak everywhere
Player registry Canonical player records, position eligibility, injury status, team affiliation Mixed Identity drift. Use Yahoo player keys as canonical from day one
Stat ingestion Nightly box score pull, idempotent upsert, correction reconciliation, backfill Own NBA stats get revised after the fact; a non-idempotent pipeline silently desyncs
Roster & lineup Slot assignment, eligibility validation, per-player game-time locking Own Locking is per-player, not per-day. Richest source of correctness bugs in the app
Scoring engine Category aggregation over a fantasy week, matchup resolution, win/loss/tie Own Must be a pure recompute over stored stat lines, never an accumulating tally
Schedule & standings Round-robin matchup generation, records, tiebreakers Mixed Low. Generate the full season once, up front
Transactions Add/drop, roster size and legality validation, transaction log Own Concurrent adds on the same player. Needs real constraints, not application-level checks
Commissioner admin Override any roster, execute trades, correct scores, import post-draft rosters Delegate Load-bearing despite being unglamorous — it is the escape hatch for everything deferred
Identity & access Accounts, league membership, authorization Delegate Use a managed provider. Nothing here is differentiating
Web client Lineup screen, matchup screen, player pool, standings Delegate The matchup screen is the one people stare at daily; give that one real attention

The three that must be yours

Lineup locking

A slot locks when that player's game tips, not at a daily cutoff. Layer on fantasy-day boundaries and a 10 p.m. ET tip-off that is already tomorrow in UTC, and this becomes the subsystem most likely to produce a silent, expensive, mid-season bug. It is also the one worth twenty minutes of interview conversation.

Scoring as pure recompute

The engine should be a pure function from stored stat lines to a matchup result, callable at any time for any week. Store raw box scores; never store an accumulated total as the source of truth. This is what makes stat corrections, rule changes, and your own bugs recoverable instead of catastrophic.

Player identity

Rosters are transcribed from a Yahoo draft, so Yahoo's player keys are your join key throughout. Name-matching will fail on suffixes, accents, and two-way call-ups — and it will fail mid-season, when fixing it is expensive.

Architecture note

Keep ingestion behind a provider interface. Yahoo is a hard single point of failure for the entire season; nba_api and balldontlie are viable fallbacks. Behind an interface, swapping is a weekend. Without one, it is a rewrite.

Sequencing

01Aug 17–23

Integration spike and foundation

Nothing else starts until Yahoo is proven. Register the app, get a token round-trip working with automatic refresh, and pull one real night of box scores end to end. In parallel: schema, deploy pipeline, CI.

Exit criteria
  • OAuth round-trip with unattended token refresh
  • One night of real box scores persisted
  • Skeleton app deployed to a live URL, CI green
02Aug 24–30

Player registry and ingestion pipeline

Turn the spike into a real pipeline behind the provider interface. Full player universe with eligibility and injury status, syncing on a schedule.

Exit criteria
  • Nightly job syncs the full player universe
  • Re-running ingestion over the same night changes nothing
  • Provider interface in place with Yahoo as one implementation
03Aug 31 – Sep 6

Rosters, lineups, locking

The hardest correctness week. Slot eligibility, then per-player locking verified against a real game night rather than against your own assumptions.

Exit criteria
  • A legal lineup can be set; illegal slot assignments are rejected
  • Players lock individually at tip-off, verified against live games
  • Fantasy-day boundaries hold for late tip-offs
04Sep 7–13

Scoring, matchups, standings

The engine, built as a pure recompute. Generate the full season schedule once and derive standings from resolved matchups.

Exit criteria
  • A 9-cat matchup resolves entirely from stored stat lines
  • Any past week can be recomputed on demand and matches
  • Full-season schedule generated; standings update from results
Gate · halfway

The daily loop should be demoable end to end with seeded data. If it is not, invoke cut list items 1 and 2 now rather than at week 7.

05Sep 14–20

Transactions and commissioner tools

Add/drop with real database constraints against concurrent claims. Commissioner override, and the post-draft roster import you will depend on in week 8.

Exit criteria
  • Add/drop enforces roster size and legality under concurrency
  • Commissioner can edit any roster and execute a trade
  • Roster import from CSV works against a realistic file
06Sep 21–27

The daily-loop interface

Three screens people actually use, on a phone, because that is where lineups get set. Real accounts and league membership replace whatever stub you have been using.

Exit criteria
  • Lineup, matchup, and player pool screens usable on mobile
  • Auth and league membership real, not stubbed
  • Someone other than you can set a lineup without instruction
07Sep 28 – Oct 4

Shadow run and hardening

Preseason games are live. Run the whole pipeline against them unattended and let real data find the bugs your fixtures could not.

Exit criteria
  • Five consecutive nights of unattended ingestion with no manual intervention
  • A stat correction reconciles without desync
  • Error alerting reaches you when a job fails
Gate · go / no-go

If the shadow run is not green, week 8 becomes hardening and the league starts on nightly-only scoring with a manual commissioner backstop. Do not start a season on an unproven pipeline.

08Oct 5–11

Onboarding and buffer

Deliberately underloaded. This week absorbs slippage from any of the previous seven, and it is the only reason the plan survives contact.

Exit criteria
  • Real post-draft rosters imported and verified
  • League members invited and signed in
  • README and architecture doc written while decisions are fresh

Cut list

Invoke in this order. Each entry is pre-decided so that a bad week costs you a feature, not a weekend of deliberation about which feature.

1 In-game stat polling → nightly ingestion only Scores refresh the next morning instead of live. The single biggest saving available. ≈ 4–5 days
2 IL slots Injured players occupy active roster spots. Annoying in basketball, survivable for one season. ≈ 2 days
3 Commissioner UI → seed scripts and direct database access You do it by hand. Only you are affected, which is what makes this cheap. ≈ 3 days
4 Player pool filtering and sorting → name search only Finding a streamer gets tedious. Pure UX cost, no correctness risk. ≈ 2 days
5 Standings tiebreakers → arbitrary but stable ordering Matters only near playoff seeding, which is months away. ≈ 1 day
Never cut
  • Per-player game-time locking
  • Idempotent ingestion
  • Scoring as a pure recompute over stored stat lines
  • Yahoo player keys as canonical identity

These four are either unrecoverable mid-season or the reason the project is worth building. Cut features around them.

Open questions

  • Confirmed 2026–27 season start date, and whether preseason games appear in Yahoo's stat feed at all — week 7 depends on it.
  • Yahoo's actual rate limits and access token TTL. Published sources disagree; measure it in week 1.
  • League size and roster configuration — drives schedule generation and slot validation.
  • Whether the commissioner is you. If not, the admin tooling needs to be usable by someone else, which moves it off the cut list.
